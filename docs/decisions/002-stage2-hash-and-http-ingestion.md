# Decision 002 — Canonical parsed-row hash and authenticated HTTP replay

**Date:** 2026-10-28. **Status:** Accepted for Stage 2. **Resolves:** Q-06.

`row_sha256` remains the Stage 1 parsed-field hash. The named contract is `hsb-parsed-fields-json-v1`, owned by `packages/shared/src/hsb.ts` and used by both the local importer and HTTP path. For the pinned HSB 1.1.0 semicolon CSV, parse every field as a string; construct an object with exactly the 16 published header names in published header order; serialize with JavaScript `JSON.stringify` without whitespace; take SHA-256 of its UTF-8 bytes and encode lowercase hex. The hash is **not of raw CSV bytes**. The field strings are not trimmed, parsed as numbers, or normalized before hashing. The adapter version remains `hsb-event-1.0.0` because this is the already-applied Stage 1 hash behavior, now specified exactly. Existing hashes are not rewritten. The 1,000 Stage 1 rows replayed over HTTP as 1,000 duplicates and zero conflicts/new rows; see `tools/bench/results/stage1-http-replay.json`.

An event's identity is `(source_manifest_id, csv:physical-line-number)`, scoped to the verified archive SHA-256 and adapter version. The client sends the physical CSV line and all source fields; it cannot send a hash, volume, or provenance label. The server verifies a pinned manifest in PostgreSQL, verifies the CSV file checksum on startup, maps each CSV physical line to its canonical hash, validates the sensor tuple against the audited 214-sensor profile, converts the explicitly inferred m³ `value` to integer mL, and derives `observed_source_measurement` provenance. A new key whose hash differs from the server-held archive line is rejected. A changed payload under an existing key is a durable conflict, never an overwrite. Repeated sensor/timestamp rows with different physical lines remain separate events.

The HTTP endpoint accepts a server-held bearer ingestion credential. It caps JSON at 1 MiB and batches at 500 events. A malformed envelope writes nothing. Valid envelopes may contain individually rejected events; accepted events, the batch report, and conflict records commit in one PostgreSQL transaction before the response. Retry after a timeout or restart is safe. Runtime queries use `app_rw` in the private `app` schema. Migration 003 adds batch and conflict records; migrations 001 and 002 remain unchanged. A failed transaction rolls back accepted events and audit rows. The endpoint emits a request ID and Pino JSON status, duration, batch ID, and outcome counts without credentials or usage values.

The published CSV is a positive, zero-filtered event file. The server's archive verification establishes that accepted rows match its pinned published source, but it does not make them complete billing intervals or certified apartment volumes. Q-05's m³ inference remains unresolved; any event sum is analytics with that caveat. A future source archive or changed hash semantics requires a new adapter version and forward migration rather than reinterpreting this version's stored rows.

Implementation follows the current [Express 5 middleware and error-handler contract](https://expressjs.com/en/guide/using-middleware/), [node-postgres transaction requirement to use one client for BEGIN/COMMIT/ROLLBACK](https://node-postgres.com/features/transactions), [Zod safeParse boundary behavior](https://zod.dev/basics), [CSV Parse's `info.lines` record metadata](https://csv.js.org/parse/options/info/), [PostgreSQL 18 `ON CONFLICT` and `RETURNING`](https://www.postgresql.org/docs/18/sql-insert.html), and [Pino's structured log/redaction API](https://github.com/pinojs/pino/blob/main/docs/api.md).
